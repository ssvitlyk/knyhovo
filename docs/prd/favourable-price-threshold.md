# PRD — «Вигідна ціна»: серверний поріг для price-alert

**Статус:** Чорновик · створено 2026-07-26 · автор: рев'ю UX конфігуратора сповіщень

## Проблема

Режим сповіщення `favourable-price` («Вигідна ціна») **не має серверної реалізації**. Клієнт мусить сам вигадати `targetPrice` і надіслати його в `PUT /api/wishlist/:bookId/alert`; API приймає будь-яке додатне число без перевірки (`packages/api/src/wishlist/alert/schema.ts`, `service.ts` — `setAlert` пише `targetPrice` дослівно). `agent_docs/alert-engine.md:78` фіксує це прямо: «favourable-price | Сприятлива ціна (алгоритм — TBD)».

Веб брав за поріг `typicalRange.min` з `GET /api/books/:id/price-history`. Наслідок, який видно в UI:

- `typicalRange` рахується **по одному вибраному листингу** (`selectListing`), а `currentPrice` на сторінці книги — це **мінімум по всіх провайдерах**. Це різні бази.
- Якщо записаних точок < 5, API згортає `typicalRange` до `lowest`/`highest` (`price-history/mapper.ts`), тобто для свіжо заінджещеної книги `typicalRange.min` **дорівнює поточній ціні**. Саме тому конфігуратор показував однакову цифру для «Нижче за поточну» і «Вигідна ціна».

Тимчасово (без зміни API) фронтенд ховає режим за гейтом `resolveFavourableTarget` (`packages/web/src/lib/alerts.ts`): поріг показується лише коли точок ≥ 5 **і** він строго нижчий за поточну ціну; інакше режим неактивний із підписом «Визначаємо вигідну ціну» і **без цифри**. Це прибирає дублювання, але не робить режим корисним.

## Чого не існує сьогодні

- Жодного поля/ендпойнта з recommended / fair / profitable ціною для книги.
- `min90` (найнижча за 90 днів) рахується, але **лише** в `packages/api/src/wishlist/buying-opportunities/engine.ts` і віддається лише через `GET /api/wishlist/buying-opportunities` — по всьому вішлисту авторизованого користувача, не по одній книзі. Сторінка книги його прочитати не може.

## Пропозиція (мінімальна зміна контракту)

Розширити наявний `GET /api/books/:id/price-history` одним необов'язковим полем — **без нового ендпойнта, без нових таблиць і колонок**:

```jsonc
{
  // ... наявні поля без змін
  "recommendedTarget": {
    "amount": 21900,            // копійки
    "currency": "UAH",
    "basis": "lowest-90d",      // 'lowest-90d' | 'typical-range'
    "sampleSize": 34,           // скільки записаних точок стоїть за цифрою
    "computedFrom": "all-listings"
  } | null                       // null, доки даних недостатньо
}
```

Правила обчислення (перевикористовують уже наявну логіку):

1. База — `min90` з `buying-opportunities/engine.ts` (мінімум по точках за 90 днів, **без** останньої точки), але агрегований **по всіх листингах книги**, а не по одному вибраному — щоб збігатися з базою `lowestPrice` у `GET /api/books/:id`.
2. `recommendedTarget = null`, якщо `sampleSize < 5` **або** значення ≥ поточної найнижчої in-stock ціни. Сервер не віддає порогу, який неможливо досягти або який дублює «Нижче за поточну» — це переносить наявний фронтенд-гейт на сервер, де він і має бути.
3. `basis: 'typical-range'` — резерв на випадок, якщо продукт захоче м'якший поріг (trimmed-діапазон) замість історичного мінімуму.

Опційно (окремим кроком, не блокує): валідація в `PUT .../alert` — для `intent: 'favourable-price'` приймати лише `targetPrice`, що дорівнює серверному `recommendedTarget`, інакше `422`. Це прибирає можливість клієнту вигадати «вигідну ціну».

## Суміжний баг, який варто закрити тим самим PR

`deriveAlertStatus` (`packages/api/src/wishlist/alert/service.ts`) вважає ціль досягнутою при `lowestPrice <= targetPrice`. Для режимів «Будь-яке зниження» і «Нижче за поточну» поріг = поточна ціна, тож алерт читався як `triggered` одразу після створення, без жодного зниження. Фронтенд зараз обходить це, зберігаючи поріг на **1 копійку** нижче поточної ціни (`resolveTargetAmount`). Правильний фікс — порівняння `<` (строго) для цих двох intents на сервері; після нього обхід у клієнті треба зняти.

Додатково: `docs/prd/wishlist.md:86` фіксує, що email-тригер W4b працює лише для `custom-price` та `favourable-price`; `any-drop` і `below-current` позначені як v2 і **листів не надсилають**, хоча UI дає їх обрати. Це окреме продуктове рішення: або дотягнути тригер, або не показувати ці режими.

## Definition of done

1. `recommendedTarget` віддається для книг із достатньою історією і `null` для решти; ніколи не дорівнює поточній ціні й ніколи не вище за неї.
2. Веб бере поріг «Вигідної ціни» лише з `recommendedTarget`; `resolveFavourableTarget` та обхід із «−1 копійка» видалені.
3. `basis`/`sampleSize` показані в UI як підстава («Найнижча за 90 днів — 219 ₴»), щоб цифра була доказовою, а не магічною.
4. Тести: агрегація по кількох листингах, межа `sampleSize = 5`, значення ≥ поточної ціни → `null`.
