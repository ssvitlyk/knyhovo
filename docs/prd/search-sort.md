# PRD: Сортування результатів пошуку (Search Sort)

**Статус:** Затверджено · 2026-07-11
**Розблоковує:** дозволене v1.1-розширення frozen-патерну Search Results v1.0 («"Найпопулярніші" / "Новинки" chips return once the API gains a sort parameter»).

## 1. Проблема

Сторінка `/search` показує єдиний вимкнений chip «Найдешевші спочатку» — сортування
не працює ні на десктопі, ні на мобільній версії, бо `GET /api/search` не має
`sort`-параметра (W9a свідомо його виключив; популярність/новинки були віднесені
до W9b/W9c). Користувач не може подивитися популярні книги чи новинки у видачі.

## 2. Рішення

### 2.1 API — `GET /api/search` отримує `sort`

| Значення | Порядок | Джерело даних |
|----------|---------|---------------|
| `price_asc` (default, без параметра — так само) | найнижча ціна ↑ | `lowestPrice.amount` (поточна поведінка, зворотно сумісно) |
| `popular` | wishlist-count ↓ | `prisma.wishlistItem.groupBy({ by: ['canonicalBookId'], _count })` — той самий механізм, що `findWishlistCounts` у collections |
| `newest` | `createdAt` ↓ | `CanonicalBook.createdAt` — та сама семантика, що `newest` у collections (дата появи в каталозі, не дата видання; відоме обмеження, успадковане свідомо) |

- Невалідне значення `sort` → 400 (як інші помилки валідації schema).
- Тай-брейки детерміновані: `popular` → ціна ↑ → `id`; `newest` → ціна ↑ → `id`
  (правило тестування: жодної недетермінованості).
- Сортування виконується в JS у `service.ts`, як і сьогодні (задокументований
  MVP-компроміс, переноситься в SQL пізніше разом з рештою).
- `SearchItemDto` **не змінюється** — wishlist-count потрібен лише для впорядкування,
  на клієнт не віддається.

### 2.2 Web — desktop: три chips (frozen-спека v1.0)

`SortControls` рендерить три chips: **Найдешевші спочатку** (default) ·
**Найпопулярніші** · **Новинки** — рівно так, як передбачає заморожений патерн.
Активний chip = `selected`; вибір міняє `?sort=` в URL і скидає `page` до 1
(заморожене правило «Sort change resets to page 1»). Запит `q` зберігається.

### 2.3 Web — mobile (<768px): дропдаун за наявним патерном

Chips ховаються; замість них — той самий кастомний listbox-дропдаун, що вже
реалізований для мобільної версії Collection Details (`.cd-sort`:
`__btn`/`__val`/`__caret`/`__menu`/`__opt`, aria-haspopup/role="listbox",
full-width, 48px висота кнопки). Логіка URL-синхронізації ідентична SortBar:
вибір → `?sort=` + скидання пагінації. Жодного нового візуального стилю —
повторне використання наявного компонента/CSS-рецепта.

UI-значення й підписи узгоджені з `lib/collections/sort.ts`
(`popular`/`newest`/`price_asc`), мапінг UI → API 1:1.

## 3. Тести

- **API integration** (`search.route.test.ts`): кожне значення `sort` + default +
  невалідне значення (400) + детермінованість тай-брейків; фейковий Prisma
  розширюється підтримкою `wishlistItem.groupBy`.
- **Web unit** (Vitest/jsdom): SortControls — рендер трьох chips, активний стан
  з URL, посилання/навігація скидає page; дропдаун — відкриття/вибір/aria.

## 4. Non-goals

- Жодних змін frozen-візуалу картки, SearchBar, пагінації, empty state.
- Жодних нових полів у `SearchItemDto` / нових ендпоінтів.
- Перенесення пошуку в SQL — окрема робота (refresh-architecture-w10).
- Сортування за релевантністю/рейтингом — поза скоупом.
